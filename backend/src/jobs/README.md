Rotinas agendadas de agregação/cache de períodos anteriores (otimização de consultas).

- `vendasPeriodoCache.job.js` — agrega vendas válidas por dia em `vendas_periodo_cache`. Rodar: `npm run job:cache-vendas [-- --desde AAAA-MM-DD]` (escreve no banco do ERP; ver cabeçalho do arquivo para o comportamento).
- `vendasProdutoCache.job.js` — agrega vendas válidas por dia e por produto em `vendas_produto_dia_cache` (quantidade, faturamento, custo CMV) e mantém `primeira_venda_produto`. Rodar: `npm run job:cache-produtos [-- --desde AAAA-MM-DD]` (escreve no banco do ERP; exige a migration 004 aplicada). Recalcula os últimos 7 dias; `--desde` preenche os dias ainda não fechados. Para cada dia grava por último uma linha sentinela (`produto = 0`) que marca "dia completo": a API só considera coberto um dia cuja sentinela foi gravada depois do fim dele. Deve rodar pelo menos uma vez após 00:00 para que "ontem" fique coberto. Ver cabeçalho do arquivo.
- `jobsComum.js` — helpers de data, trechos e `--desde` usados pelo job por produto.
- `agendarJobsDiarios.js` — orquestrador diário: roda `job:cache-vendas` e depois `job:cache-produtos` (cada um em processo Node separado, porque os dois fecham a pool de conexão global ao final), decide sozinho se precisa de `--desde` (quando percebe, por um estado gravado em `backend/estado-jobs/ultima-execucao.json`, que ficou 2+ dias sem rodar com sucesso) e grava log em `backend/estado-jobs/jobs-diarios.log`. Rodar: `npm run job:diario`. É o comando pensado para agendamento — ver `backend/scripts/agendar-tarefa-windows.md` para o comando exato do Agendador de Tarefas do Windows (não executado automaticamente por ninguém; requer confirmação do usuário para rodar contra qualquer banco).
- Preenchimento inicial (obrigatório): rodar `--desde` a partir da primeira venda do ERP, fora do horário de uso (varredura pesada). Sem ele, `crescimento` e `queda` respondem 503 nos períodos ainda não cobertos. Para `/novos` a API **não** protege contra a falta do preenchimento: a guarda só barra períodos que começam antes da primeira venda registrada, então, se o histórico não foi carregado, produtos antigos que voltaram a vender aparecem como "novos" sem aviso.
- Premissas de operação: não agendar o job perto de 00:00 (corrida de meia-noite: o dia pode ficar "fechado" com dados parciais até o próximo recálculo de 7 dias) e conferir que o fuso da sessão do MariaDB é o mesmo do dia de negócio (`SELECT @@time_zone, NOW()`, somente leitura), pois o critério de dia fechado compara `atualizado_em` com o início do dia seguinte.
